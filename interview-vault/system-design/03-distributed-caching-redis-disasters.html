💡 Ví dụ hình dung đời thực cho 3 Thảm họa Cache (Nhớ ngay lập tức không bao giờ nhầm):
  1. 🦬 Cache Stampede / Breakdown (1 Key siêu "Hot" vừa hết hạn): Giống như Bảng niêm yết điểm thi Đại học dán ngoài cổng trường vừa bị gió thổi rách đúng lúc 10.000 phụ huynh đang đứng xem ➔ Cả 10.000 người đồng loạt xô đổ cửa phòng Hiệu trưởng (SQL Database) chỉ để hỏi cùng 1 bảng điểm đó!
  2. 👻 Cache Penetration (Đâm xuyên vì hỏi ID KHÔNG TỒN TẠI, ví dụ id = -999): Giống như kẻ xấu thuê 10.000 người đến hiệu thuốc hỏi mua "Thuốc trường sinh bất tử". Cô nhân viên tìm trên kệ ngoài quầy (Redis Cache) không thấy, lại phải chạy vào tận kho tổng (SQL DB) lục tung lên cũng không có. Vì không có nên cô cũng chẳng cất lên kệ ngoài ➔ Người thứ 2, thứ 10.000 hỏi câu y hệt lại bắt cô chạy vào kho tổng!
  3. 🏔️ Cache Avalanche (Tuyết lở — 100.000 Key cùng hết hạn đúng 12h đêm): Giống như siêu thị hẹn giờ tất cả 100.000 mặt hàng trên kệ đều hết hạn đúng 00:00:00. Đúng 00:00:01, toàn bộ khách hàng hỏi mua bất kỳ món gì cũng phải chờ nhân viên chạy vào kho tổng lấy lại từ đầu!
💡 Real-Life Mental Analogies for the 3 Cache Disasters (Zero Confusion):
  1. 🦬 Cache Stampede / Breakdown (1 Ultra-Hot Key Expires): Like the University Exam Bulletin Board at the front gate falling down right when 10,000 parents are looking at it ➔ All 10,000 parents simultaneously storm the Principal's office (SQL DB) asking for the exact same score sheet!
  2. 👻 Cache Penetration (Querying Non-Existent Data, e.g., id = -999): Like an attacker sending 10,000 people to a pharmacy asking for an "Elixir of Immortality". It's not on the front shelf (Redis), so the clerk runs to the back warehouse (SQL DB) and finds nothing. Because nothing was found, nothing is placed on the front shelf ➔ All 10,000 requests hit the warehouse directly!
  3. 🏔️ Cache Avalanche (100,000 Keys Expire at the Exact Same Second): Like setting all 100,000 products on the front shelves to expire at midnight 00:00:00 sharp. At 00:00:01, every single customer request misses the shelf and floods the warehouse!

2. Classic Question: On Write, Should You "Update DB Then Delete Cache" or Vice Versa?

Nhiều ứng viên trả lời sai là "Xóa Cache trước rồi mới Update DB" hoặc "Update cả DB lẫn Cache". Hãy nhìn ví dụ thực tế dưới đây để thấy tại sao chuẩn công nghiệp bắt buộc phải là: (1) Update SQL Database trước ➔ (2) Xóa (Invalidate) Redis Cache sau:

  • ❌ Nếu Update Cache thay vì Xóa Cache: Nếu 2 luồng A (sửa giá = 100k) và B (sửa giá = 200k) chạy song song: Trong SQL, A ghi trước B ghi sau (SQL = 200k), nhưng do mạng trễ nên B lại ghi Redis trước rồi A ghi đè Redis sau (Redis = 100k) ➔ Lệch dữ liệu vĩnh viễn cho tới khi hết TTL!
  • ✅ Chuẩn Cache-Aside: Cập nhật SQL thành công ➔ Gọi DEL product:123 trên Redis (Nếu muốn an toàn tuyệt đối với các hệ thống Read cực lớn, dùng thêm Delayed Double Delete: Xóa Cache ➔ Đợi 300ms ➔ Xóa lại lần nữa hoặc dùng Debezium CDC lắng nghe binlog SQL để xóa Cache).

Why is the industry standard for Cache-Aside Pattern strictly: (1) Update SQL Database First ➔ (2) Delete (Invalidate) Redis Key Second?

  • ❌ Why NOT Update Cache directly? If Thread A (price=100) and Thread B (price=200) run concurrently: A updates SQL first, B updates SQL second (SQL=200), but due to network jitter B updates Redis first and A overwrites Redis second (Redis=100) ➔ Permanent stale cache until TTL expires!
  • ✅ Standard Cache-Aside: Commit to SQL first ➔ DEL product:123 in Redis (with optional Delayed Double Delete or CDC binlog invalidation).
// Chống Cache Stampede + Penetration + Avalanche trong .NET 8
public async Task<ProductDto?> GetProductByIdAsync(long productId, CancellationToken ct)
{
    // 1. Chặn ngay ID bất hợp lệ (Chống Cache Penetration bước 1)
    if (productId <= 0) return null;

    string cacheKey = $"product:detail:{productId}";
    var db = _redis.GetDatabase();

    // 2. Đọc từ Redis
    var cachedJson = await db.StringGetAsync(cacheKey);
    if (cachedJson.HasValue)
    {
        if (cachedJson == "__NULL__") return null; // Hit Null Cache!
        return JsonSerializer.Deserialize<ProductDto>(cachedJson!);
    }

    // 3. Cache Miss ➔ Dùng Semaphore / Distributed Lock chống Cache Stampede
    string lockKey = $"lock:product:{productId}";
    string lockToken = Guid.NewGuid().ToString("N");

    if (await db.StringSetAsync(lockKey, lockToken, TimeSpan.FromSeconds(5), When.NotExists))
    {
        try
        {
            var product = await _sqlRepo.FindByIdAsync(productId, ct);
            if (product is null)
            {
                // Lưu "__NULL__" với TTL ngắn 2 phút (Chống Penetration)
                await db.StringSetAsync(cacheKey, "__NULL__", TimeSpan.FromMinutes(2));
                return null;
            }

            // Cộng TTL Jitter ngẫu nhiên 1..15 phút (Chống Cache Avalanche)
            var jitter = TimeSpan.FromMinutes(Random.Shared.Next(1, 15));
            await db.StringSetAsync(cacheKey, JsonSerializer.Serialize(product), TimeSpan.FromMinutes(60) + jitter);
            return product;
        }
        finally
        {
            await ReleaseLockSafelyAsync(db, lockKey, lockToken);
        }
    }

    // Các luồng khác không lấy được lock: chờ 40ms rồi đọc lại từ Cache
    await Task.Delay(40, ct);
    return await GetProductByIdAsync(productId, ct);
}
