Người phỏng vấn Senior luôn muốn thấy bạn đi từ giải pháp rẻ nhất, ít đập phá kiến trúc nhất rồi mới nâng cấp dần theo quy mô dữ liệu:

  • Giai đoạn 1 (1M ➔ 20M dòng): Sửa câu Query + Đánh Covering Index (INCLUDE) + Bỏ phân trang OFFSET thay bằng Keyset/Cursor Pagination. (Chi phí: 0đ, nhanh gấp 100 lần!).
  • Giai đoạn 2 (20M ➔ 80M dòng): Tách Đọc/Ghi (1 Master Write + 3 Read Replicas) + Bọc Redis Cache.
  • Giai đoạn 3 (80M ➔ 200M dòng): Table Partitioning theo tháng + Data Archiving (Đẩy đơn hàng cũ trên 1 năm sang kho lưu trữ lạnh Cold Storage / ClickHouse).
  • Giai đoạn 4 (200M ➔ 1 Tỷ+ dòng): Horizontal Sharding (Chia nhỏ dữ liệu ra nhiều Server vật lý theo TenantId hoặc MerchantId + Dùng Snowflake 64-bit ID).
💡 Golden Interview Rule: "Never Jump Straight to Sharding in Your First Sentence!"

Senior interviewers test your engineering judgment—always progress from lowest complexity & highest ROI to distributed sharding:

  • Stage 1 (1M ➔ 20M rows): Query tuning + Covering Indexes (INCLUDE) + Replace OFFSET pagination with Keyset/Cursor Pagination. (Cost: $0, 100x speedup!).
  • Stage 2 (20M ➔ 80M rows): Read/Write Splitting (1 Master + 3 Read Replicas) + Redis Caching.
  • Stage 3 (80M ➔ 200M rows): Table Partitioning by month + Cold Data Archiving (move orders > 1 year old to Cold DB).
  • Stage 4 (200M ➔ 1B+ rows): Horizontal Sharding across physical DB nodes by TenantId / MerchantId + Snowflake 64-bit IDs.

1. Hình vẽ Hệ thống: Xử lý lỗi "Replication Lag" (Vừa tạo đơn xong F5 lại không thấy đơn!)

1. System Diagram: Solving "Replication Lag" (Read-Your-Own-Writes Consistency)

Ví dụ thực tế: Khi tách Master DB (Chuyên Ghi) và Read Replica DB (Chuyên Đọc), quá trình đồng bộ từ Master sang Replica mất khoảng 200ms - 800ms. Nhưng khách hàng vừa bấm "Tạo đơn hàng" xong, trình duyệt lập tức chuyển trang (Redirect) sang trang "Danh sách đơn hàng" trong vòng 50ms và đọc vào Read Replica ➔ Replica chưa kịp nhận dữ liệu mới nên khách hàng hoảng hốt tưởng "Mất tiền mà không có đơn!"

Real-World Scenario: Replication from Master DB (Write) to Read Replica DB (Read) takes 200ms–800ms. Right after a user creates an order, the UI redirects to "My Orders" within 50ms and queries the Read Replica ➔ The new order hasn't replicated yet, so the user panics thinking their order vanished!

2. Ví dụ thực tế: Tại sao phân trang OFFSET 1000000 làm treo SQL, còn Keyset Pagination chỉ mất 1ms?

2. Concrete Example: Why OFFSET 1000000 Freezes SQL While Keyset Pagination Takes 1ms

  • 🐢 Cách chậm (Offset Pagination): SELECT * FROM Orders ORDER BY Id DESC OFFSET 1000000 ROWS FETCH NEXT 20 ROWS ONLY ➔ SQL Server vẫn phải lôi cổ cả 1.000.020 dòng lên đĩa/RAM, đếm bỏ đi 1.000.000 dòng đầu rồi mới trả về 20 dòng cuối! Càng lật trang sâu (trang 50.000), DB càng chậm cấp số nhân (~8 giây).
  • 🚀 Cách siêu tốc (Keyset / Seek Pagination): Nhớ LastSeenId của dòng thứ 20 ở trang trước (ví dụ LastSeenId = 8500120) rồi truyền vào câu tiếp theo: SELECT TOP 20 * FROM Orders WHERE Id < 8500120 ORDER BY Id DESC ➔ Cây B-Tree Clustered Index nhảy (Seek) thẳng tới vị trí 8500120 và nhặt đúng 20 dòng kế tiếp! Dù ở trang 1 hay trang 100.000 cũng chỉ mất 0.8ms!
  • 🐢 Slow (Offset Pagination): SELECT * FROM Orders ORDER BY Id DESC OFFSET 1000000 ROWS FETCH NEXT 20 ROWS ONLY ➔ SQL Server still scans through 1,000,020 rows just to discard the first 1,000,000! Deep pages take ~8 seconds.
  • 🚀 Ultra-Fast (Keyset / Cursor Pagination): Pass the last row's ID from the previous page (LastSeenId = 8500120): SELECT TOP 20 * FROM Orders WHERE Id < 8500120 ORDER BY Id DESC ➔ B-Tree Index performs a direct Index Seek to 8500120 and reads only 20 rows. Page 100,000 is just as fast as Page 1 (0.8ms)!
