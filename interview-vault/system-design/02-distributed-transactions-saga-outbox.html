💡 Ví dụ hình dung đời thực (Đặt Tiệc Cưới Trọn Gói = Nhà hàng + Ban nhạc + Nhiếp ảnh):
  • 🐢 Two-Phase Commit (2PC) — "Bắt cả 3 nơi giữ máy điện thoại chờ nhau": Bạn gọi điện cho Chủ nhà hàng, Ban nhạc và Thợ ảnh, bắt cả 3 người cùng giữ máy không được tiếp khách khác. Bạn hỏi: "Cả 3 sẵn sàng chưa?" (Phase 1). Nếu Thợ ảnh đi vào thang máy mất sóng 30 giây, cả Nhà hàng và Ban nhạc cũng bị treo máy đứng hình theo! ➔ Nghẽn toàn hệ thống, không thể mở rộng (Scale).
  • 💃 Saga Choreography — "Nhảy chuyền tay không có người chỉ huy": Nhà hàng đặt bàn xong tự nhắn cho Ban nhạc; Ban nhạc nhận lịch xong tự nhắn cho Thợ ảnh. Với 2-3 bên thì nhanh, nhưng nếu đám cưới có 8 dịch vụ (Hoa tươi, Xe dâu, MC, Trang điểm...) mà bước thứ 7 bị lỗi, các bên tự nhắn ngược để hủy sẽ tạo thành mạng nhện vòng lặp (Cyclic Dependency) không ai biết đơn đang kẹt ở đâu!
  • 🎼 Saga Orchestration — "Có 1 Nhạc trưởng / Wedding Planner điều phối trung tâm (MassTransit / Temporal)": Một người quản lý duy nhất cầm cuốn sổ trạng thái (State Machine): Bước 1 gọi Kho giữ hàng ➔ Bước 2 gọi Ví trừ tiền. Nếu Ví báo "Không đủ tiền!", Nhạc trưởng lập tức phát lệnh Compensating (Giao dịch bù trừ): Yêu cầu Kho nhả hàng ra và đóng đơn!
💡 Real-Life Mental Analogy (Booking a Wedding Package = Venue + Band + Photographer):
  • 🐢 Two-Phase Commit (2PC) — "Forcing all 3 vendors to stay on hold on a conference call": You call the Venue, Band, and Photographer and force all three to lock their schedules and stay on the line. If the Photographer enters an elevator and loses signal for 30 seconds, the Venue and Band are completely blocked from serving any other customers!
  • 💃 Saga Choreography — "Relay chain without a leader": The Venue texts the Band; the Band texts the Photographer. Great for 2-3 services, but with 8 services, if step 7 fails, everyone texting everyone else to cancel turns into an unmanageable spaghetti cycle.
  • 🎼 Saga Orchestration — "A Central Wedding Planner / Conductor (MassTransit State Machine)": One central coordinator holds the checklist: Step 1 Reserve Inventory ➔ Step 2 Charge Wallet. If Payment fails (Insufficient funds), the Planner immediately issues Compensating Transactions backward: Release Inventory and Mark Order Failed!

2. The "Dual-Write" Trap & Transactional Outbox Pattern Diagram

Câu hỏi bẫy cực hay gặp ở MoMo / TymeX: "Trong Order Service, sau khi anh gọi await _db.SaveChangesAsync() để lưu đơn hàng xong, dòng tiếp theo anh gọi await _kafka.PublishAsync() nhưng đúng lúc đó mất mạng hoặc sập nguồn Pod Kubernetes thì sao?"

  • ❌ Hậu quả nếu viết code bình thường: Đơn hàng đã nằm trong SQL Database, nhưng Kafka không bao giờ nhận được message ➔ Kho không trừ, Thanh toán không chạy ➔ Đơn hàng "ma" (Zombie Order) bị treo vĩnh viễn!
  • ✅ Giải pháp chuẩn: Transactional Outbox Pattern — Thay vì bắn trực tiếp lên Kafka, ta lưu luôn quả tin nhắn đó vào bảng OutboxMessages nằm chung trong cùng 1 ACID Transaction SQL với bảng Orders!

Classic Trap Question at MoMo / TymeX: "In Order Service, right after await _db.SaveChangesAsync() commits to SQL, what happens if the Kubernetes Pod crashes or network drops right before await _kafka.PublishAsync() executes?"

  • ❌ Consequence of Naive Code: The order is saved in SQL, but the Kafka event is lost forever ➔ Inventory and Payment never trigger ➔ Inconsistent Zombie Order!
  • ✅ Production Solution: Transactional Outbox Pattern — Instead of calling Kafka directly inside the HTTP request, insert the event payload into an OutboxMessages table inside the exact same local SQL ACID Transaction as the Orders table!

3. Chống Trừ Tiền 2 Lần bằng Idempotency Key (Khi mạng lag hoặc Kafka gửi lặp)

3. Preventing Double Charging with Idempotency Keys (Network Retries & Duplicate Events)

Ví dụ thực tế: Khách hàng bấm nút "Chuyển 5.000.000đ" trên app ngân hàng. Yêu cầu đã tới Server và trừ tiền xong, nhưng đúng lúc trả kết quả về thì 4G bị rớt mạng. App tự động gửi lại (Retry) yêu cầu đó lần thứ 2! Làm sao Payment Service nhận ra đây là cùng 1 giao dịch để không trừ mất 10.000.000đ?

Real-World Scenario: A user taps "Transfer 5,000,000 VND". The server deducts the money, but the mobile 4G connection drops before the HTTP 200 response arrives. The mobile app automatically retries the exact same request! How does Payment Service avoid deducting 10,000,000 VND?

// PaymentController.cs — Xử lý Idempotency-Key chống trừ tiền 2 lần
[HttpPost("charge")]
public async Task<IActionResult> ChargeWallet(
    [FromHeader(Name = "Idempotency-Key")] string idempotencyKey,
    [FromBody] ChargeRequest request)
{
    if (string.IsNullOrWhiteSpace(idempotencyKey))
        return BadRequest("Missing Idempotency-Key header");

    var redisKey = $"idempotency:payment:{idempotencyKey}";
    var db = _redis.GetDatabase();

    // 1. Thử chiếm khóa nguyên tử trên Redis (SET NX với TTL 24 giờ)
    bool isFirstRequest = await db.StringSetAsync(
        redisKey, "PROCESSING", TimeSpan.FromHours(24), When.NotExists);

    if (!isFirstRequest)
    {
        // Request bị lặp! Kiểm tra xem lần trước đã xử lý xong chưa:
        var existingState = await db.StringGetAsync(redisKey);
        if (existingState == "PROCESSING")
            return Conflict(new { message = "Giao dịch đang được xử lý, vui lòng không bấm lặp!" });

        // Trả lại y hệt kết quả của lần thành công trước đó mà KHÔNG trừ tiền lại!
        return Ok(JsonSerializer.Deserialize<ChargeResponse>(existingState!));
    }

    // 2. Lớp bảo vệ cuối cùng ở Database: Unique Constraint trên cột IdempotencyKey
    var response = await _paymentService.ExecuteDebitInSqlTransactionAsync(request, idempotencyKey);

    // 3. Lưu kết quả vào Redis để nếu client retry thì trả về ngay
    await db.StringSetAsync(redisKey, JsonSerializer.Serialize(response), TimeSpan.FromHours(24));
    return Ok(response);
}
